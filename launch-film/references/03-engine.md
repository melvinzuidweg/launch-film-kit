# 03 · The engine: a film as a pure function of time

Every frame of the film is computed from one number, the time `t`. There is no animation state that builds up while the film plays. This file explains that architecture, the API the starter template exposes, the contracts that let several agents build acts in parallel, and the pitfalls that broke determinism in the Griffel case.

The code excerpts are adapted from the Griffel source (`examples/griffel/src/`) with the product copy removed. The starter project in `assets/template/` uses the same architecture and the same API names. A few file names differ: the template's logo geometry is `src/logo.js` (the case's `mark.js`, generated by `tools/logo_from_svg.mjs`), its single example act is `src/parts/act-example.js` (the case had `act-a.js` … `act-e.js`), and it renders with `tools/render.mjs` instead of the case's `render.sh`. The template also adds `Film.tok()` (read colours from `tokens.css`) and `Film.sfx()` (register extra sound cues); see its `README.md`.

## 1. Why seek(t)

The rule: **every animated style is set from `t` inside `render(t)`, every frame.** No timers, no CSS transitions or keyframe animations, no `requestAnimationFrame`, no `Date`, no `Math.random`.

What that buys you:

- **Any frame is reproducible.** `window.__seek(24.0)` always produces the same picture, whatever was rendered before. A critic can render its own evidence at exact times ("at 22.05 the option is not selected yet") and a fixer can check the same frame after the fix. Review notes become precise and checkable instead of "somewhere in the middle it feels off".
- **A fix is one edit plus a re-render of the affected seconds.** Nothing has to be replayed from the start, so a fixer can iterate on a 0.5 s window with a handful of stills.
- **Parallel capture.** Each render worker takes a time range and seeks into it directly. The final render captured 23,000-25,000 frames per format with four workers.
- **Motion blur by supersampling.** Capturing at 480 fps and averaging 8 subframes into each 60 fps frame only works if the page can be seeked to arbitrary sub-frame times.
- **Global retiming is one number.** The whole film was slowed by `T.SCALE = 120/110` late in the project to fit the music (§5). In a timer-driven page that would have been a rewrite.
- **Variants are cheap.** A variant page swaps the first three seconds and is identical afterwards (§12).

What it costs: you write motion as math, not as fire-and-forget tweens, and you think of every on-screen state as derived. That is real extra effort for UI that has state (a list that loses a row after a tap, a field that fills while typing). The pattern is always the same: compute the state from `t` and the schedule, then set the styles. The marketing website's existing HTML rebuilds of the app screens ran on intervals and animation libraries, so they could not be reused as-is and had to be ported to this model.

## 2. Pages and load order

One HTML page per format, all loading the same scripts:

| Page | Format | Set before the scripts |
|---|---|---|
| `index.html` | 16:9, 1920×1080 | `window.FORMAT = "169"` |
| `portrait.html` | 4:5, 1080×1350 | `window.FORMAT = "45"` |
| `index-<variant>.html`, `portrait-<variant>.html` | same | plus `window.VARIANT = "<variant>"` |

Load order, and why it is in that order:

```
gsap            only as the runtime bridge for HyperFrames (optional; see 05)
engine.js       pure math: easing, springs, noise, colour. No DOM, no Film.
timeline.js     window.T: every time in the film. Reads nothing but window.TIME_SCALE.
copy.js         window.COPY: every visible string.
mark.js         logo geometry generated from the brand SVG (do not hand-edit)
film.js         window.Film: layers, camera, phone, taps, pushes, type, render loop
parts/*.js      stage, phone, act-a ... act-e, pushes, overlay-text, touch: each calls Film.register
boot            window.Film.boot()
```

Parts register themselves when their script runs; nothing mounts until `Film.boot()` (or the first `Film.render`) calls `mountAll()`. So the order of `<script>` tags for parts does not matter for correctness; the `order` field decides render order (§4).

The pages carry no static `data-duration` on the root element. If you render through HyperFrames, a static value overrides the one set from script and the render silently uses the wrong length (see `08-gotchas.md`). The template's own render path does not need HyperFrames (see `05-render-and-encode.md`).

## 3. Layers and coordinate systems

`film.js` builds four absolutely positioned layers inside `#root`:

| Layer | z | Space | Holds |
|---|---|---|---|
| `stage` | 0 | screen | background gradient, rings, the dark act, the "example" label |
| `world` | 10 | world (camera-transformed) | the phone and anything that should move with the camera |
| `overlay` | 20 | screen | chapter cards, meeting captions, claim lines |
| `top` | 30 | screen | anything that must sit above the overlay |

Three coordinate systems:

- **screen**: output pixels, 1920×1080 or 1080×1350. Overlay text lives here, so it never scales with the camera and stays at a size you chose for feed readability.
- **world**: camera space. The phone's centre is the world origin (0, 0), and 1 world px = 1 logical app px at zoom 1.
- **phone**: the app screen's logical coordinates, 0..393 × 0..852 (iPhone logical size), origin top-left. Taps and in-app layout use these.

The camera maps world to screen:

```js
// film.js, Film.render: one transform on the world layer per frame. 2D translate(), not
// translate3d(): the case used translate3d, and a later test showed it makes the raster depend
// on the frames painted before (§10); the template uses translate()
const c = Film.camera.at(t);
ctx.world.style.transform =
  `translate(${L.W / 2}px, ${L.H / 2}px) scale(${c.z.toFixed(5)}) ` +
  `translate(${(-c.cx).toFixed(3)}px, ${(-c.cy).toFixed(3)}px)`;

// screen = (world - camera centre) * zoom + frame centre
Film.toScreen = function (wx, wy, t) {
  const c = Film.camera.at(t);
  return { x: (wx - c.cx) * c.z + L.W / 2, y: (wy - c.cy) * c.z + L.H / 2, z: c.z };
};
```

`Film.phoneToWorld(x, y, t)` applies the phone's own motion (position, scale, rotation) and `Film.phoneToScreen(x, y, t)` chains both. Acts use these to land an object exactly on a UI element while camera and phone both move, and to check that world content stays out of the overlay text box.

A framing helper in `timeline.js` answers the question you actually have when placing the camera: "put phone point (lx, ly) at screen point (sx, sy) at zoom z":

```js
const frame = (W, H) => (lx, ly, sx, sy, z) => ({
  cx: +(lx - PHONE_W / 2 - (sx - W / 2) / z).toFixed(2),
  cy: +(ly - PHONE_H / 2 - (sy - H / 2) / z).toFixed(2),
  z,
});
// e.g. pin the top of the phone screen just under a 4:5 text box:
// f45(PHONE_W / 2, 0, 540, 445, 1.15)
```

Inside the phone screen the z-order is fixed: act screens 1-40, status bar 50, push banners 60, dynamic island 70, touch dot 80. Acts build their screens as absolute 393×852 children of `ctx.phone.screen`, which clips.

## 4. The Film API

### Registering a part

```js
Film.register({
  id: "act-b",
  order: 30,             // lower renders first; later parts may override styles
  mount(ctx) { /* build DOM once, register keys */ },
  render(t, ctx) { /* set every animated style from t */ },
});
```

`ctx` carries `Film`, `T`, `COPY`, `Eng`, the layout `L`, `PHONE`, `format` and the layers (`stage`, `world`, `overlay`, `top`, and after the phone part mounts, `ctx.phone.screen`). Render order in the case: phone 5, acts 30, overlay text 80, pushes 85, touch 90. The template's example act uses 20. Any value between the phone (5) and the overlay text (80) works for an act; give all acts the same value unless one has to override another's styles. One catch: the case's `film.js` sorted with `(order || 50)`, so the stage's declared `order: 0` actually counted as 50. The template sorts with `??`, so 0 means first; if you port code from the example, keep that in mind.

`Film.render` wraps every part's `mount` and `render` in `try/catch`. A part that throws on mount is marked broken and skipped; a render error is logged with the part id and the time. One broken act therefore does not blank the film, and the stills tool prints the error as `PAGE ERRORS` so the builder sees it.

### A minimal act

```js
(function () {
  const { Film, Eng } = window;
  const { P } = Eng;
  let B, root, card;

  Film.register({
    id: "act-b",
    order: 30,
    mount(ctx) {
      B = ctx.T.B;                                           // this act's times
      root = Film.el("div", "abs", ctx.phone.screen, {
        left: 0, top: 0, width: ctx.PHONE.w + "px", height: ctx.PHONE.h + "px", zIndex: 12,
      });
      card = Film.el("div", "abs card", root, { left: "20px", top: "180px" }, ctx.COPY.app.cardTitle);

      // the schedule is data, registered once
      const bc = Film.handoff("BC");                         // shared framing with the next act
      Film.camera.key(B.pushIn[0], B.pushIn[1], { z: 1.3 });
      Film.camera.key(ctx.T.handoff.BC.t - 1.0, 1.0, bc);    // end ON the hand-off framing
      Film.push({ t: B.push[0], dur: B.push[1], title: ctx.COPY.push.ready.title,
                  body: ctx.COPY.push.ready.body, tapAt: B.tapPush });
      Film.tap({ t: B.tapPush, x: 196.5, y: 100 });
      Film.tap({ t: B.tapConfirm, x: 196.5, y: 640 });
      Film.darkScreen([B.start, B.lightAt]);                 // status bar turns white here
    },
    render(t) {
      const on = t >= B.start && t < B.end;
      root.style.visibility = on ? "visible" : "hidden";     // root of this act: visible/hidden
      if (!on) return;
      const u = P(t, B.cardIn, 0.45);                        // house curve by default
      card.style.opacity = u.toFixed(3);
      card.style.transform = `translate(0, ${(12 * (1 - u)).toFixed(2)}px)`;   // 2D inside the world (§10)
    },
  });
})();
```

Why keys are registered at mount and not computed in `render`: the whole schedule exists before frame 0. `touch.js` uses it to plan one-finger glides between taps, the audio tool (`events.mjs`) reads the registered taps and pushes to generate the sound-effect cue list, and a critic can dump `Film.camera.at(t)` for every frame to measure camera speed.

### API summary

| Call | What it does |
|---|---|
| `Film.camera.key(t, dur, {cx?, cy?, z?}, ease?)` | Camera move. Keys compose in start order; each lerps from the state the earlier keys left, so overlapping keys blend. Zoom interpolates in log space. |
| `Film.camera.at(t)` | The camera state at `t` (for measuring and clipping). |
| `Film.handoff("AB")` | The shared framing between two acts for this format, from `T.handoff` (§9). |
| `Film.phoneMotion.key(t, dur, {x?, y?, s?, r?}, ease?)` | Phone position, scale (log space) and roll inside the world. |
| `Film.tap({t, x, y, hold?})` | One touch-dot press at phone logical coords, at the exact centre of the control. |
| `Film.push({t, dur, title, body, tapAt?})` | An OS-style push banner: slides down from under the island, holds, leaves upward. |
| `Film.darkScreen([from, to])` | Declares a window where the app screen is dark, so the status bar turns white. |
| `Film.stageDark(t, x, y)` | 0 (light) to 1 (dark) at a screen point. Overlay text and labels pick their colour from it. |
| `Film.type.make(parent, text, cls, style, {whole?})` | Splits text into masked words (or one block with `whole: true`). |
| `Film.type.render(block, t, tIn, tOut?, {stagger?, dur?, exitDur?})` | Word-by-word rise in from `tIn`; block exit from `tOut`. |
| `Film.type.goneAt(tOut)` | When the exiting block is fully gone (at most `tOut + 0.3`). |
| `Film.frameT(t)` | Film time quantised to the output frame grid (§5). |
| `Film.toScreen`, `Film.phoneToWorld`, `Film.phoneToScreen` | Coordinate conversions (§3). |
| `Film.el(tag, cls, parent, style, text)` | Small DOM helper. |
| `window.__seek(tOut)` | Renders an output time. Used by the stills and capture tools. |
| `window.__seekFilm(t)` | Renders a film time (debugging; `still.mjs --film`). |

### Camera keys

```js
Film.camera = {
  key(t, dur, to, ease = E.house) { camKeys.push({ t, dur, to, ease }); camKeys.sort((a, b) => a.t - b.t); },
  at(t) {
    let s = Object.assign({}, L.cam0);                 // the rest framing for this format
    for (const k of camKeys) {
      const u = k.ease(clamp((t - k.t) / k.dur));
      if (u <= 0) continue;
      if (k.to.cx !== undefined) s.cx = lerp(s.cx, k.to.cx, u);
      if (k.to.cy !== undefined) s.cy = lerp(s.cy, k.to.cy, u);
      if (k.to.z !== undefined) s.z = zoomLerp(s.z, k.to.z, u);
    }
    return s;
  },
};
```

Practical consequences:

- **Zoom in log space** gives constant perceived speed: 1 → 2 feels like 2 → 4. A linear zoom lerp starts slow and ends fast when zooming in.
- **Overlap keys to avoid stop-start.** A key that starts while the previous one is still easing blends out of motion instead of from rest. Back-to-back keys were a recurring motion-critic note ("staccato" in round 2), and camera was the lowest sub-score, 5, in round 3.
- **Set a start state with a tiny key before 0:** `Film.camera.key(-1, 0.001, c0)`.
- **Linear keys for creeps.** A slow push under a long hold should run at constant speed (`E.linear`) with only a soft start and stop; an eased creep reads as a stall at its end.

### Taps and the touch dot

A phone app is driven by a finger, so the film shows a touch dot, not a cursor (a cursor reads as desktop). Per tap: the dot appears 0.32 s before `t`, presses at `t`, releases at `t + hold`, and is gone 0.22 s later, with a ripple on the press.

One finger: when the next tap follows less than 0.6 s after a release, the same dot glides to the next target (house curve, at most 0.22 s) instead of a second dot appearing. In round 2 the critics flagged two dots on screen during quick recipient taps; it read as multi-touch or a ghost cursor.

```js
// touch.js: chain the taps once (taps are registered at mount, so the plan is static)
const GLIDE_GAP = 0.6;
if (cur.t - (prev.t + prev.hold) < GLIDE_GAP) {
  const end = cur.t - 0.07;
  const start = Math.max(prev.t + prev.hold + 0.1, end - 0.22);
  plan[i] = { from: j, glide: [start, end - start] };
}
```

Hold-to-press controls use `hold` (the real hold duration from the app, 1.2 s in the case).

### Overlay type

Chapter cards and claim lines use one type system:

- **Entry:** each word sits in an `overflow: hidden` mask and rises from 105 % below with an opacity ramp, staggered (default 0.06 s per word, 0.65 s per word on the house curve).
- **Exit:** the whole block leaves as one unit: a small rise, a fade and at most 4 px of blur over 0.25 s (never more than 0.3 s). Per-word exits were the first design; at feed size they left dangling fragments, a single word floating over the phone after the rest had gone.
- **Rule:** never two cards in the text box at once. Every card's `Film.type.goneAt(out)` must be at or before the next card's `in`. `timeline.js` encodes this in comments next to every card.
- **Colour from the stage:** overlay text reads `Film.stageDark` under its own position each frame and mixes ink to white, so a card that rises while the lights go down stays readable.

```js
render(block, t, tIn, tOut = Infinity, o = {}) {
  const stagger = o.stagger ?? 0.06, dur = o.dur ?? 0.65;
  const exitDur = Math.min(o.exitDur ?? 0.25, 0.3);
  block.words.forEach((w, i) => {
    const u = P(t, tIn + i * stagger, dur, E.house);
    w.inner.style.transform = `translate3d(0, ${((1 - u) * 105).toFixed(2)}%, 0)`;
    w.inner.style.opacity = clamp(u * 1.4).toFixed(3);
  });
  if (Number.isFinite(tOut)) {
    const ex = P(t, tOut, exitDur, E.house);
    block.el.style.opacity = (1 - ex).toFixed(3);
    block.el.style.transform = ex > 0 ? `translate3d(0, ${(-0.12 * ex).toFixed(4)}em, 0)` : "none";
    block.el.style.filter = ex > 0.001 ? `blur(${(4 * ex).toFixed(2)}px)` : "none";
  }
  block.el.style.visibility = t < tIn - 0.01 || t > tOut + exitDur + 0.01 ? "hidden" : "visible";
}
```

A reading hold should never be a frozen frame. The overlay layer carries a 2 px sine drift, and the camera usually creeps under long holds. A critic measures frozen runs (see `07-qa-checklist.md`), and "text on a static frame" is the first thing a muted feed scrolls past.

### Runtime hooks

`Film.boot()` mounts everything, writes the output length into the root's `data-duration`, installs `window.__seek(tOut)` and `window.__seekFilm(t)`, and renders frame 0. If you render through HyperFrames, boot also registers a paused GSAP timeline whose single proxy tween calls `Film.render` on update and listens for the `hf-seek` event; the template's own capture tool only uses `__seek`.

## 5. Film time, output time and frameT

Two clocks:

- **Film time** is what the storyboard, every `T` value and every part's `render(t)` use.
- **Output time** is the rendered video's clock: `output = film × T.SCALE`. The runtime, `window.__seek`, the stills and capture tools and the audio cue list all speak output time. `Film.render(tOut)` converts back.

Why the scale exists: the film was written on a 120 BPM grid (bar = 2.0 s, the key moment on a downbeat at film 22.0). The licensed tracks turned out to be 110 BPM. `SCALE = 120/110` makes every film beat land on a music beat with one number, and slowed the film by about 9 %, which the founder had asked for anyway. The output went from 48 s to 52.36 s with the key moment at output 24.0. A first attempt used `SCALE = 1.1`; a fresh critic measured the tracks at 110 BPM and showed that the beat-locked events drifted by up to about 0.18 s by the logo lock. Derive the scale from the BPM ratio exactly, and preferably pick the music before you build (`06-music-and-sound.md`).

```js
const SCALE = Number(G.TIME_SCALE) > 0 ? Number(G.TIME_SCALE) : 120 / 110;   // grid BPM / track BPM
const r6 = (v) => Math.round(v * 1e6) / 1e6;     // 48 * 1.1 = 52.800000000000004 otherwise

const T = {
  DURATION: 48.0, DROP: 22.0, SCALE, OUT_FPS: 60,
  get OUT_DURATION() { return r6(this.DURATION * this.SCALE); },  // getters: a page may change
  get OUT_DROP() { return r6(this.DROP * this.SCALE); },          // DURATION/SCALE before boot
  toOut(t) { return r6(t * T.SCALE); },
  toFilm(t) { return Math.round((t / T.SCALE) * 1e9) / 1e9; },   // snapped: output 24.0 -> film 22.0
};
```

Change `T.DURATION` or `T.SCALE` only before `Film.boot()`. After a change, regenerate the audio cue list and re-align the music edit.

### frameT: text whose value changes

The final render captures 480 fps and averages 8 subframes into each 60 fps output frame. A timer computed from raw `t` changes its digits several times inside one output frame; the 8 subframes then show different digits, and the average is a grey smear. Any text whose value changes (timers, counters, typed characters, a bold/regular switch) takes its value from `Film.frameT(t)`:

```js
// film time quantised to the OUTPUT frame grid, so all 8 subframes of a frame agree
Film.frameT = function (t) {
  const S = T.SCALE, F = T.OUT_FPS || 60;
  return Math.floor(t * S * F + 1e-6) / F / S;
};

// usage, in the recording screen's timer
const tq = Film.frameT(t);
const sec = from + (to - from) * P(Math.min(tq, stopT), start, end - start, E.house);
```

`Math.floor(t * 60) / 60` looks equivalent but quantises to the film grid, which stops lining up with output frames as soon as `SCALE != 1`. The `1e-6` guards against floating-point values that land just below a frame boundary. For a 30 fps delivery the page must quantise to 30: the template's `render.mjs --fps 30` passes `--out-fps 30` to the capture, which sets `T.OUT_FPS` before the first seek. If you capture some other way, set `T.OUT_FPS` yourself before seeking.

## 6. Easing: the house curve and closed-form springs

### One curve

Every morph and camera move uses one curve, `cubic-bezier(.45, 0, .15, 1)`: a gentle start and a long, soft landing. Durations vary (0.35-1.2 s); the curve does not. One curve is what makes many separately built acts read as one hand. When critics proposed an accelerating curve for a snap, triage rejected it and got the same effect by shortening the move.

Exceptions that were kept on purpose:

- **Linear** for creeps and drifts that should have constant speed (§4).
- **OS-native motion** for system UI the viewer knows, such as the push banner sliding in.

`engine.js` solves the bezier per call with Newton iterations and a bisection fallback:

```js
function bezier(x1, y1, x2, y2) {
  const cx = 3 * x1, bx = 3 * (x2 - x1) - cx, ax = 1 - cx - bx;
  const cy = 3 * y1, by = 3 * (y2 - y1) - cy, ay = 1 - cy - by;
  const sx = (s) => ((ax * s + bx) * s + cx) * s;
  const sy = (s) => ((ay * s + by) * s + cy) * s;
  const dsx = (s) => (3 * ax * s + 2 * bx) * s + cx;
  return (u) => {
    if (u <= 0) return 0;
    if (u >= 1) return 1;
    let s = u;
    for (let i = 0; i < 8; i++) {                    // Newton
      const err = sx(s) - u, d = dsx(s);
      if (Math.abs(err) < 1e-7 || Math.abs(d) < 1e-6) break;
      s -= err / d;
    }
    // ...bisection fallback if Newton did not converge
    return sy(s);
  };
}
const E = { house: bezier(0.45, 0, 0.15, 1), linear: (u) => clamp(u) /* , out, in, inOut, soft */ };

// eased progress of a move that starts at `start` and lasts `dur`
const P = (t, start, dur, ease = E.house) => ease(clamp((t - start) / dur));

// 0 before a, ramps in, 1, ramps out before b
function win(t, a, b, fadeIn = 0.3, fadeOut = 0.3, ease = E.house) { /* ... */ }
```

`P` is the workhorse: almost every line of act code is `const u = P(t, start, dur)` followed by a style computed from `u`.

### Closed-form springs

Where something should arrive with mass and settle, use a damped spring evaluated in closed form, so it is still a pure function of time (no integration, no state from the previous frame):

For damping ratio ζ < 1, with ω = 2πf and ω_d = ω·√(1 − ζ²):

```
x(τ) = 1 − e^(−ζωτ) · ( cos(ω_d τ) + (ζω / ω_d) · sin(ω_d τ) )
```

For ζ ≥ 1 (critically damped):

```
x(τ) = 1 − e^(−ωτ) · (1 + ωτ)
```

`τ` is the time since the spring started; `x` goes from 0 to 1.

```js
function spring(tau, f = 2.2, z = 0.9) {
  if (tau <= 0) return 0;
  const w = 2 * Math.PI * f;
  if (z >= 1) return 1 - Math.exp(-w * tau) * (1 + w * tau);
  const wd = w * Math.sqrt(1 - z * z);
  return 1 - Math.exp(-z * w * tau) * (Math.cos(wd * tau) + ((z * w) / wd) * Math.sin(wd * tau));
}

// a value that changes target several times: one spring per change, summed
function S(t, base, changes, f, z) {         // changes: [[t0, to], [t1, to], ...]
  let v = base, prev = base;
  for (const [t0, to] of changes) { v += (to - prev) * spring(t - t0, f, z); prev = to; }
  return v;
}
```

The defaults (f = 2.2 Hz, ζ = 0.9) overshoot by e^(−πζ/√(1−ζ²)) ≈ 0.15 % and settle within about 0.3 s. Keep ζ ≥ 0.9: bouncy springs read as playful, which fights a calm, precise product tone. The only deliberate settle in the case was one 4 % scale settle on the logo lock.

### Other helpers in engine.js

```js
const zoomLerp = (a, b, u) => Math.exp(lerp(Math.log(a), Math.log(b), u));   // camera zoom

function hash(n) {                         // deterministic pseudo-random in [0, 1)
  const s = Math.sin(n * 127.1 + 311.7) * 43758.5453123;
  return s - Math.floor(s);
}
function noise1(x) {                       // smooth 1D value noise
  const i = Math.floor(x), f = x - i, u = f * f * (3 - 2 * f);
  return lerp(hash(i), hash(i + 1), u);
}
// mixHex(a, b, u), hexToRgb(h), typed(str, t, start, cps)
```

A live waveform, for example, is `noise1(seed + barIndex + floor(t / 0.09))` mapped to the app's real bar-height range: it scrolls one bar per 90 ms like the app, and every frame is reproducible.

## 7. timeline.js and copy.js: one source of truth each

### timeline.js

All times live in `window.T`. Acts read them at runtime and never hard-code a time that exists there; times an act needs internally are derived from `T` (`const tAdvance = C.tapAnswer + C.autoAdvance`).

```js
const BPM = 120, BEAT = 60 / BPM, BAR = BEAT * 4;
const bar = (n) => (n - 1) * BAR;                // start of bar n (1-based): bar(12) = 22.0

const T = {
  BPM, BEAT, BAR, bar, DURATION: 48.0, DROP: 22.0, /* SCALE etc., see §5 */

  dark: { inStart: 2.0, inDur: 3.4, spread: 0.3, outStart: 9.8, outDur: 0.8 },
  label: [-0.4, 38.6],                           // "example" label visible while fictional content is legible

  handoff: {                                     // shared framings between acts (§9)
    AB: { t: 10.0, "169": { cx: -362, cy: 6, z: 1.06 }, "45": { cx: 0, cy: -226, z: 1.15 } },
  },

  A: { start: 0.0, end: 10.6, phoneEnter: [1.8, 1.1], timer: { start: 2.0, end: 9.4 }, holdStop: [8.4, 1.2] },
  B: { start: 9.8, end: 16.6, pushSpeakers: [11.6, 1.0], tapPush: 12.35, /* ... */ },

  O: {                                           // overlay cards; `out` = starts leaving, gone by out + 0.3
    ch1: { in: 3.4, sub: [3.7, 4.0], subOut: 6.0, out: 10.0 },
    climax: { a: 24.0, b: 24.25, out: 25.85 },
  },
};
```

Conventions that paid off:

- **Act windows overlap on purpose.** The incoming act's screen covers the outgoing one, so there is never a gap or a hard cut between acts.
- **Every value carries its reason.** In the case, `timeline.js` became the film's decision log: comments such as "fix 3: the marker sweep lands before 1.0, so the hook has a real visual event in its first second" next to the number. When a later critic asks to move it, triage can see why it is where it is.
- **Whole-bar grid from day one.** Put key events on bar or beat boundaries (`bar(n)`), so the music edit can cut in whole bars (`06-music-and-sound.md`). Critic suggestions that moved events off the grid were skipped in triage.
- **One owner.** `timeline.js` changes ripple through every act. Acts propose changes in their reports; only the lead session or one foundation fixer edits the file (see `04-build-and-critique.md`).

### copy.js

Every visible string lives in `window.COPY`, grouped by where it appears (hook, captions, chapter cards, claims, end card, app UI, pushes, e-mail):

```js
window.COPY = {
  label: "Example meeting",
  hook: { line: "...", key: "...", question: "..." },
  ch1: { word: "Record.", sub: ["...", "..."] },
  app: {
    // verbatim from the product's i18n file; key names in comments
    recLive: "...",            // record.live
    questionsStep: (x, y) => `Step ${x} of ${y}`,
    // ...
  },
  push: { questions: { title: "...", body: "..." } },   // the real push copy, from the backend source
};
```

Why a separate file: the brand/truth critic and triage need one place to check every claim against the facts file; copy fixes never touch act files; an English version is a `copy.js` swap plus a layout check for longer or shorter lines. When an act needs a string that is not in `copy.js` yet, it may inline it with a comment naming the source key, and asks the copy owner to move it.

## 8. The ownership contract

Several agents build and fix in parallel, so file ownership is the main defence against them breaking each other's work.

- **One file per act** (`src/parts/act-a.js` ... `act-e.js`), owned by one builder or fixer at a time. A helper you need goes into your own file, even if that duplicates code elsewhere. Duplication is cheaper than two agents editing a shared helper.
- **Foundation files** (`engine.js`, `film.js`, `timeline.js`, `copy.js`, `tokens.css`, `stage.js`, `phone.js`, `touch.js`, `pushes.js`, `overlay-text.js`, the pages, the tools) belong to the lead session, or to one foundation fixer per round.
- **Acts register their own keys** (camera, phone motion, taps, pushes, dark-screen windows) at mount, inside their own time window.
- **Requests go in reports, not edits.** A builder that needs a time change writes "`T.O.trust.out` 37.8 → 37.3, because ..." in its report. The lead collects these "for other owners" lists between rounds.
- **Each act file starts with a long header comment** describing what happens when, in film time, with the reasons. Critics, fixers and triage read headers first to understand who owns what. Keep it updated with every fix; in the case the headers were the most accurate description of the film.
- **Shared side effects are documented and reset.** Act E changed the shared phone's styles from 40.5 on (dissolving the frame into the logo). That is allowed only if the act restores them for every earlier `t`, so seeking backwards still gives the original phone (see §10).

The contract is written into the storyboard's non-negotiables so every agent reads it before touching code.

## 9. Geometry contracts between acts

Anything that crosses an act boundary needs fixed numbers that both sides use. In the case:

- **The recording waveform:** 36 bars, 4 px wide with 4 px gaps (284×72), centred at phone logical (196.5, 430), heights from the app's real mapping with seeded noise. Act A morphs the hook's words into it, act B folds its bars into the processing step dots, act E collapses them into the logo's bars. Act B copied act A's noise seed so the bars at the hand-off are identical.
- **The overlay text box and the captions box** per format (`L.text`, `L.captions` in `film.js`). World content stays out of the text box while overlay text is visible; acts check it with `Film.toScreen`.
- **The label position** and size per format.
- **Hand-off framings.** The first contract said "every act returns to the rest camera by the end of its window". The motion critic measured six zoom reversals in seven seconds around one act: the camera pulled out to rest only to push in again for the next act. The fix was a shared framing per boundary:

```js
// timeline.js: the outgoing act ends ON this framing (landed by t); the incoming act starts FROM it
handoff: {
  AB: { t: 10.0, "169": { cx: -362, cy: 6, z: 1.06 }, "45": f45(196.5, 0, 540, 445, 1.15) },
  BC: { t: 16.3, "169": f169(196.5, 110, 1340, 300, 1.45), "45": f45(196.5, 0, 540, 440, 1.25) },
  DE: { t: 38.0, "169": { cx: -255, cy: 0, z: 0.94 }, "45": { cx: 0, cy: -120, z: 0.8 } },
},

// film.js
Film.handoff = (k) => (T.handoff && T.handoff[k] ? { ...T.handoff[k][FORMAT] } : { ...L.cam0 });
```

The rule became: end on `Film.handoff("XY")` when a hand-off is defined, start from it in the next act, otherwise return to rest.

- **Pixel-exact object hand-offs.** When an object travels from one act's world into the phone (words becoming bars), its end point is recomputed every frame from `Film.phoneToWorld`, so it lands exactly even while the camera and phone move.

Geometry contracts have a cost: once acts measure against them (act D clipped the e-mail card at a screen y computed from `Film.camera.at(t)`; act E's logo lock point was computed from the phone corners), late global changes become risky. Triage rejected a camera smoothing filter in `film.js` late in the project for exactly that reason. Settle the foundation geometry before the act builds, and treat later changes as foundation work with every act re-checked.

## 10. Determinism pitfalls

Every item here happened in the case, except the 3D-transform row, which a later test of the template found. The test that catches most of them is the **seek-order test**: render the same times in two different orders and compare the pixels. `tools/still.mjs` normally seeks in ascending order, like the capture; `--order listed` makes it seek in the order you list the times. Include at least one backward seek across every exit and scale change of the phone (the template's phone leaves at 7.35-8.0, so 7.8 → 3 below), because that is where history-dependent raster state shows:

```bash
node tools/still.mjs --page portrait.html --times 2,3,4,6,7.8,10 --out renders/det/fwd
node tools/still.mjs --page portrait.html --times 10,7.8,3,6,2,4 --order listed --out renders/det/shuf
```

Run it for both pages (`index.html` and `portrait.html`).

```python
import glob, os, sys, numpy as np
from PIL import Image
a, b = sys.argv[1], sys.argv[2]
for f in sorted(glob.glob(os.path.join(a, "t_*.png"))):
    x = np.asarray(Image.open(f).convert("RGB"), np.int16)
    y = np.asarray(Image.open(os.path.join(b, os.path.basename(f))).convert("RGB"), np.int16)
    d = np.abs(x - y).max(axis=2)
    print(os.path.basename(f), "max diff", int(d.max()), "pixels > 2:", int((d > 2).sum()))
```

| Symptom | Cause | Fix |
|---|---|---|
| Text from one act ghosts through the rest of the film. | A child set to `visibility: visible` overrides a hidden parent. | Children use `inherit`; only the act's root toggles `hidden`/`visible`. |
| Frames differ depending on what was rendered before (the seek-order test fails along edges of scaled elements). | `will-change: transform` makes Chrome keep a raster at the scale it was first painted at. | No `will-change` on anything that scales; the word spans of the type system deliberately avoid it. The case used it once, on a slowly drifting hook block whose glyph baselines otherwise snapped between whole pixels (frame diff alternating 0.8 / 0.25), and only after verifying it with the seek-order test. |
| Layout positions are 8-39 px off their words. | Measurement ran before the web font loaded. `document.fonts.status` already reads "loaded" before any face has been requested. | Check the specific face, `document.fonts.check("700 96px Inter")`, and measure lazily until it is true; or use constant sizes measured once by hand, so the layout never depends on load timing. The tools also wait for `document.fonts.ready`. |
| Fonts missing in stills, fallback font everywhere. | Chrome blocks font loads on `file://`. | The stills and capture tools serve the project over a local HTTP server. |
| Different output on every render. | `Math.random`, `Date`, `requestAnimationFrame`, `setTimeout`, CSS transitions or keyframe animations. | Seeded `hash`/`noise1`; everything from `t`. |
| A timer or counter smears into grey in the final render. | Its value changes inside one output frame across the 8 blur subframes. | `Film.frameT(t)` (§5). |
| An element shows a stale state only when you seek backwards. | A style was set for a window but never reset for times before it (act E's end-card gradient). | Compute every style every frame, or gate the element's visibility and set all its styles whenever it is visible. |
| A full-frame crossfade jitters (single-frame diffs up to about 5). | Chrome composites in 8 bits, so the whole frame steps one level at once. | A tiny alpha slope across each fading sheet (±1.5/255 corner to corner) spreads the steps out. |
| After a backward seek, the phone's status bar and island are drawn 1 px off (edge differences up to 255 levels). A fading screen's text differs by about 50 levels from a fresh render, or the screen's straight edges by about 35, even in forward order. | `translate3d()` on the world layer, the phone or the screens inside it gives each its own compositor layer, and Chrome keeps raster state from frames it painted earlier. After the phone was painted at scale 0.96 during its exit, a seek back to t = 3 snapped the status bar differently. Opacity was not the cause; forcing it to 1 changed nothing. | Inside the world (the world layer, the phone and everything in it), animate with 2D transforms: `translate()`, `scale()`, `rotate()`, never `translate3d()`. The template does this since that test. Afterwards 24 times in shuffled order matched the forward render in both formats, stills matched the capture within 2 levels, and the motion curves matched the old render (correlation 0.9998); only some text edges land a sub-pixel differently. The overlay, top and stage layers are not scaled by the camera and may keep `translate3d()`. |
| Small differences (a few levels) along moving edges after out-of-order seeks. | Chrome's rasteriser. | Harmless; the capture tool has each worker seek strictly forward through its own range, after one warm-up seek. |

Creating DOM lazily is fine (the touch layer creates one dot per registered tap on first render), as long as the element's appearance is derived from `t`.

## 11. Rebuilding real app UI from source

The phone shows a rebuild of the real app in HTML, not a screen recording. That lets the camera fly into it, keeps it sharp at any zoom and makes every frame seekable. It also creates a responsibility: the UI on screen is a claim about the product. Rules that worked:

- **Read the product's code, not its marketing.** For each screen, read the component that renders it (layout, spacing, sizes, states), the theme tokens (colours, radius, fonts) and the i18n strings. For push notifications, read the backend code that sends them; for e-mails, the e-mail templates. Put the source paths in the storyboard row for that screen so builders and critics can check.
- **Shipping CSS beats design docs.** The repo's design-token document turned out to be a stale template from another project. The live website CSS and the app's token file were right.
- **Strings verbatim.** Copy them into `copy.js` with the i18n key in a comment. Never paraphrase app UI; the brand/truth critic compares against the source.
- **Derive the layout from the component's numbers** and write them down as named constants with comments (safe-area insets, padding, gaps, line heights). A typical block from the case: the recording screen's live label, timer, waveform, description, microphone row and stop button positions, each derived from the component's paddings.
- **Exact tokens:** the radius (10 px for every app control in the case; only real circles are round), colours, type weights, selected states, icons (lucide-style icons redrawn as inline SVG with the app's stroke width and round caps).
- **Real behaviour and timing:** auto-advance after 250 ms, a 1.2 s hold-to-stop, the busy label while stopping, a list row that disappears when tapped instead of a chip popping out of nowhere. Critics catch invented behaviour.
- **Real navigation grammar:** page changes inside the app are OS-style pushes (0.35 s, incoming page from the right edge, outgoing moving −30 % and dimming 10 %, top bar fixed). A push from the right means "forward" to an iPhone user, so it is wrong for a time jump; time jumps are dissolves or light changes.
- **Simplify by omission, never by invention.** Dropping secondary controls is fine; adding a control, screen or suggestion the app does not have is not.
- **Check the claim the UI makes at code level.** In the case, three things the marketing implied were not in the code: a name suggestion only appears when a saved name literally occurs in that speaker's words (so the film shows the user typing the name), a push text the team remembered did not exist (the real one was used), and the app has no transcript or notes screen (so what is said at the table is shown as overlay captions, not as an app screen).
- **Watch for collisions between real UI and fictional data.** A real input placeholder suggested an example name that was also one of the fictional attendees. To a first-time viewer it looked like the app suggesting that name, which is the feature the film must not show. The attendee was renamed.
- **Document deliberate deviations** in the storyboard: first names instead of e-mail addresses in recipient chips, the brand font instead of the e-mail's fallback font stack, removed sections. Then triage can defend them when a critic flags them.
- **Film-only legibility settings stay outside the app UI.** The overlay type used Inter's `cv08` stylistic set (a capital I with serifs) so a line starting with a capital I does not read as a lowercase l at feed size. The rebuilt app UI stays exactly as the app renders it.

The rebuilt UI is not a valid App Store preview (stores require real screen capture). Plan store videos as a separate track; see `05-render-and-encode.md`.

## 12. Variants

A variant is the same film with a different opening (or ending): in the case, "question-first", where the film's strongest moment opens the film and everything from film time 3.2 on is identical to the original.

- **A variant page** is a copy of the original page with `window.VARIANT = "<name>"` next to `window.FORMAT`.
- **Acts branch at mount.** `const VAR = window.VARIANT === "<name>"`; the variant branch registers its own camera keys, taps and dark-screen windows. The original pages never run variant code; check that with stills of the original before and after.
- **Variant times** live in a `T.V` block that the page may pre-set before the act loads.
- **Per-variant overrides of shared times** go in an inline script on the variant page, after `timeline.js` and before the parts read it. Setting a card's time to `Infinity` hides it, because `Film.type.render` never shows a block whose `tIn` is infinite:

```html
<script>window.FORMAT = "169"; window.VARIANT = "question";</script>
<script src="src/engine.js"></script>
<script src="src/timeline.js"></script>
<script>
  // this variant already says the sub line in its hook, so the later sub is skipped
  window.T.O.ch2 = Object.assign({}, window.T.O.ch2, { sub: [Infinity, Infinity] });
</script>
<script src="src/copy.js"></script>
```

- **Converge to identical pixels.** From the point where the variant joins the original, the DOM should be the same as the original's, because the browser's layer tree affects rasterisation. The variant in the case still mounted the original hook and kept it force-hidden, so from the join point on its frames matched the original.
- **Plan variants from the start.** Shared timeline, only the hook swaps. Building it at the end worked, but it needed its own critic pass and a camera fix (the variant's pull-out created a zoom reversal the original did not have).

## 13. Formats

16:9 and 4:5 are both authored, from the same timeline, with per-format layouts in `film.js`. The case's layouts were:

```js
// the case (examples/griffel/src/film.js); the template's differ, see below
const LAYOUTS = {
  "169": { W: 1920, H: 1080, cam0: { cx: -380, cy: 0, z: 1.0 },   // phone right of centre, text left
           text: { x: 170, y: 300, w: 780 }, captions: { x: 170, y: 640, w: 780 },
           wordSize: 112, subSize: 40, capSize: 30 },
  "45":  { W: 1080, H: 1350, cam0: { cx: 0, cy: -210, z: 0.86 },   // phone low, text on top
           text: { x: 84, y: 96, w: 912 }, captions: { x: 84, y: 372, w: 912 },
           wordSize: 92, subSize: 36, capSize: 28 },
};
```

The template's `LAYOUTS` (in `assets/template/src/film.js`) differ from these:

- **Text box:** the 4:5 box starts at y 110, not 96.
- **No `captions` box:** the example has no meeting captions. Add one per format (with a `capSize`) if your film shows spoken lines.
- **Extra keys:** `stmtSize` for the statement cards, `minText` (the floor for labels and fine print; 02 §8 has the sizes for story-critical text) and `label` for the "Example" label (the case's `voorbeeld`).

Acts make their camera keys format-aware (`if (Film.format === "45")`). Recompose, do not crop: in 4:5 the text sits above the phone and the camera frames the phone lower and tighter. 9:16 is best recomposed from 4:5 later.

Feed readability decides sizes more than taste does. 4:5 is the mobile-feed format, viewed about 360 px wide, so every size is divided by 3: a 36 px caption reads as 12 px. In 16:9 at the same width everything is divided by 5.3, which is why the case treated 16:9 as the desktop and YouTube cut and judged feed readability on 4:5. Put minimum on-screen text sizes per format in the storyboard; see `02-story-and-storyboard.md`.
